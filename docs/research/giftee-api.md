調査日：2026-09-29　／　対象：CLAUDE.md「8. 未決」の「ギフティ API で使える範囲」
方法：ギフティの公開 Web ページ、giftee for Business サポートサイト（Zendesk の公開ヘルプ記事）、e街プラットフォームのサービス・事例ページ、観光DX推進協議会に掲載されたギフティの説明資料（PDF）を読んだ。ログインが必要な資料（API 仕様書本体、管理画面、e街の資料請求で出る資料）は読めていない。**書いてあることだけを書き、推測で埋めていない。** 推測や解釈には「（解釈）」と書いた。

## 1. 要約

**結論：このサービスで使いたいデータは「giftee for Business の API」ではなく、「e街プラットフォーム（e街ギフト／e街チケットポータル）の管理画面とデータ出力」から来る。公開情報で分かるのはここまでで、API で取れるかどうかは確認が必要。**

1. **ギフティには性格の違う2つの系統がある。**
   - **giftee for Business**：コンビニ・カフェなど全国ブランドの eギフトの URL を企業に卸すサービス。公開されている API は「ギフト URL の発行」と「発行済みギフトの参照（URL・有効期限など）」だけ。**利用状況・利用率は「ギフト提供元各社の情報資産のため開示できない」と公式ヘルプに明記**されている。アクセス数も非公開。→ 受取・利用の指標はここからは取れない。
   - **e街プラットフォーム**：自治体・地域向けの電子商品券・クーポン。松本市の子育て支援クーポン（e街チケットポータル）も、さっぽろ圏e旅ギフト（旅先納税）もこちら。**「管理画面からチケットの発行・受取・利用実績をリアルタイムで確認できる」「データのダウンロードも可能」「加盟店別や利用者属性別の分析」**と公式に書かれている。
2. **e街で公開情報から確認できるデータ**：発行実績／受取／利用実績（リアルタイムで管理画面に反映）、加盟店別の精算データ（締日ごとに自動生成）、会員情報、取得・購入データ。決済完了画面には「店名・決済金額・決済日時」が出る。券種は通貨型（1円単位）・もぎり型（回数券）・定期券型。
3. **e街の「API」は「外部連携・発行に対応」までしか公開されていない。** 読み出し用 API（利用履歴を外から取る API）があるかどうか、項目・粒度・更新頻度は公開情報では確認できない。
4. **アンケート**：e街はアンケート回答をクーポン取得の条件にでき、「クーポンの利用実績と紐付けて『誰が・どのように来て・いつ・どこで受け取って使ったか』等のデータ収集・分析が可能」「回答結果等の取得データは自治体に帰属」とある（インバウンド向けページ）。giftee for Business 側にも Survey（アンケート＋ギフト付与）がある。**利用後に聞く形（このサービスの ④）に対応しているかは不明。**
5. **属性との掛け合わせ**は「利用者の属性情報とチケットIDを紐付けすることが必要」と注記つきで、分析の事例として示されている。**会員登録の項目を自治体が自由に決められるか**は不明。

### ギフティに確認すべき上位5つ
1. 寄附ギフトは e街の事業の中の1券種として発行できるか。その券種だけの発行・受取・利用を分けて出せるか（企業ごとの集計の前提）。
2. 管理画面の「データのダウンロード」に入る項目は何か：1件の利用ごとに「チケットID・会員ID（仮名）・加盟店ID・日時・金額・枚数」が含まれるか。
3. 利用データを外から取る API（または定期的な CSV の自動出力）はあるか。更新はリアルタイムか日次か。
4. 会員登録の項目（子どもの人数、地区、居住地など）を事業ごとに設定でき、利用データとチケットID／会員IDで紐付けて出せるか。
5. 利用後のアンケート（消し込みの後に1分アンケートを出す）はできるか。回答を利用データと紐付けて出せるか。回答データの帰属・第三者（寄附企業）への集計値提供の扱いはどうなるか。


### 会員情報の出力が公開情報に書かれている（技術的に可能と見込む根拠）
2026-09-30 追記。ギフティに聞くときの前置きに使う（「公開資料に会員情報の出力とあったので、できるのではと考えた」程度の温度感）。

- **会員情報の出力**：e街チケットポータル提供開始のプレスリリース（2024年1月11日）の機能一覧に「各種データ出力機能（会員情報／取得・購入データ 等）」とある。松本市の子育て支援クーポンはこのチケットポータル。<https://giftee.co.jp/pressrelease20240111_02/>
- **利用実績との紐付け**：e街のインバウンド向けページに「クーポンの利用実績と紐付けることで『誰が・どのように来て・いつ・どこで受け取って使ったか』等のデータ収集・分析が可能」、回答結果等の取得データは自治体に帰属、とある。<https://emachi-platform.jp/service/inbound-marketing>
- **ここから言えること（推論）**：発行・取得されたチケットに、持ち主の会員を区別する値（会員ID）が入っていれば、利用実績と突き合わせて次が出せる。
  - 会員ごとの発行・取得数に対して、何枚使われたか
  - いつ使われたか（利用日時）
  - どこで使われたか（加盟店）
  - 会員情報に事前にプロフィール（登録項目：子どもの人数・地区・年代など）を入れておけば、属性別の集計
- **まだ分からないこと**：会員情報の出力に入る項目（登録項目か、氏名・連絡先だけか）、会員IDが利用実績の明細に入るか（説明資料の「属性情報とチケットIDの紐付けが必要」の具体的な方法）、世帯をまとめる項目があるか。
- **受け取る範囲**：このサービスが受け取るのは「仮名の会員ID＋登録項目」だけにし、氏名・住所は受け取らない前提。

#### 事例で確認できた運用
- **松本市**：LINE 公式アカウントで申請 → シリアルコード受取 → ポータルに会員登録（1家庭1回）→ クーポン取得。利用は「コード読み取り」で**店の QR を利用者が読む**＋「利用枚数設定」（[松本市のページ](https://www.city.matsumoto.nagano.jp/site/kosodate/165551.html)）。LINE 側の申請は Bot Express と連携（[説明資料 p.37](https://kanko-dx.go.jp/wp-content/uploads/2025/02/439e55f093c79a3909a92d7b0d27355a.pdf)）。市の職員は「記録がすべて電子データ化」「システム上のデータはきれいに整備されている」と話している。消防団クーポンでは「約1,700名のうち約1,000名が登録、登録者のうち実際に利用したのは半数ほど」と、**登録数と利用者数を自治体が把握している**（[松本市の導入事例](https://emachi-platform.jp/casestudy/matsumoto)）。
- **白浜町（旅先納税）**：「取得できるデータから、毎年同じ時期に来訪して旅先納税を利用してくださる方がいたり、何度も（電子商品券を）使ってくださる方の存在を把握できています」→ **同じ人の繰り返し利用を追えている**（[白浜町の導入事例](https://emachi-platform.jp/casestudy/shirahama)）。
- **柏崎市**：加盟店ごとに設置した二次元コードを利用者のスマホで読み取って決済。回数券は電子スタンプで消し込み（[柏崎市の導入事例](https://emachi-platform.jp/casestudy/kashiwazaki)）。

## 3. 指標ごとの取れる／取れない表

凡例：
- **API**＝公開情報で API から取れると確認できた
- **画面・CSV**＝公開情報で、管理画面の集計またはデータ出力（ダウンロード）で取れると確認できた
- **不明**＝公開情報では確認できない（取れないとも書かれていない）
- **新規**＝公開情報からは今の仕組みにないと読める。ギフティ側で作る必要がありそう
- **不可**＝公開情報で「開示しない」と明記

| 指標 | e街（松本・さっぽろはこちら） | giftee for Business | 根拠・補足 |
| --- | --- | --- | --- |
| 配布数（発行数） | **画面・CSV**（発行実績、リアルタイム）。API は不明 | **API**（発行ごとに URL が返る＝自社で数えられる）＋**画面**（発行実績、リアルタイム） | e街：チケットポータル FAQ、説明資料 p.12。gfB：[発行件数](https://giftee.zendesk.com/hc/ja/articles/4404343145113) |
| 受取数・受取率 | **画面・CSV**（「受取」実績、リアルタイム）。「受取」が何を指すか（シリアル入力／マイページへの取得）は不明 | **不可に近い**：URL を開いたかどうか（アクセス数）は非公開 | e街：チケットポータル FAQ。gfB：[アクセス数](https://giftee.zendesk.com/hc/ja/articles/4404524771481) |

| 継続（2回以上の利用） | **不明**（1件ごとの利用履歴に人の ID が入れば計算可） | 不可 | — |
| 周遊（2市町村以上） | **画面・CSV**の可能性（「加盟店の周遊状況の分析」「周遊データ」が例示）。出力の形は不明 | 不可 | 説明資料 p.14・p.29 |

## 4. ギフティへの確認事項リスト（打ち合わせでそのまま使える形）

### A. 前提（どの仕組みに乗せるか）
1. 寄附で届ける体験ギフトは、e街（e街チケットポータル／e街ギフト）の既存事業の中で「1つの券種」として発行できますか。giftee for Business の商品として出す案はありますか。
2. 券種ごとに「発行・受取・利用」の実績を分けて出せますか。寄附企業が複数あるとき、企業ごと（券種ごと）の集計を出せますか。
3. 一つの自治体が複数の事業（子育て・観光など）を持つとき、事業をまたいだ一覧（事業ごとの発行・受取・利用）を1回で出せますか。

### B. 管理画面・データ出力の中身
4. 管理画面の「データのダウンロード」で出せるファイルの種類と項目の一覧をいただけますか（発行実績／利用実績／精算データ／会員情報／取得・購入データ）。
5. 利用実績は1件の決済ごとの明細で出せますか。明細に次の項目は含まれますか：チケットID、会員ID（仮名）、券種、加盟店ID・加盟店名、決済日時（秒まで）、決済金額、利用枚数、決済方式（QR／スタンプ／紙券）。
6. 「受取」は何の時点を指しますか（シリアルコードを入れた時／マイページに取得した時／URL を開いた時）。受取日時は記録されていますか。
7. 加盟店マスタに「市町村」「業種」「地区」などの属性を持てますか。利用明細にその属性を付けて出せますか。
8. 家族で共有したチケットを家族の誰が使ったかは記録されますか（使った人の区別）。
9. 有効期限切れ（失効）の枚数・金額、未利用の残高は出せますか。
10. 紙券（CPM）と電子の利用は同じ明細に入り、区別できますか。

### C. API・連携・更新頻度
11. e街に、利用実績を外から読み出す API はありますか。なければ、定期的な CSV の自動出力（SFTP・クラウドストレージなど）はできますか。
12. 更新はリアルタイムですか、日次ですか。締日ごとの精算データと、リアルタイムの利用実績は別物ですか。
13. 消し込みの時に、外部へ通知（Webhook など）を送れますか。
14. API を使う場合の認証方式、IP 制限、利用料、呼び出し回数の上限はどうなりますか。
15. 松本市のように LINE（Bot Express）経由で申請する事業では、申請データと e街の会員・利用データを同じ ID でつなげられますか。

### D. 登録項目・属性
16. 会員登録の項目は事業ごとに自治体が決められますか（例：使う人、子どもの人数、いちばん下の子の年齢区分、地区／同行者の人数、居住地、年代）。
17. 登録項目を利用明細とチケットID・会員IDで紐付けて出せますか（説明資料の「属性情報とチケットIDの紐付けが必要」の具体的な方法）。
18. 年齢は区分で持てますか。生年月日しか持てない場合、出力時に区分へ変換できますか。

### E. アンケート
19. 消し込みの直後に、利用者の画面へアンケートを出せますか（取得条件ではなく、利用後に聞く形）。
20. 設問を自治体が管理画面で追加・変更でき、すぐに利用者の画面へ反映されますか。形式（5段階・1つ選ぶ・複数選ぶ・自由記述）は選べますか。
21. 回答を利用明細（チケットID・加盟店・日時）と紐付けて出せますか。
22. 外部のアンケートツールと連携する場合、利用者を識別する値（仮名ID）をアンケート側へ渡せますか。

### F. 個人情報と企業への提供
23. 「取得データは自治体に帰属」とありますが、自治体が寄附企業に**集計値だけ**を渡すことは契約上問題ありませんか。ギフティとして条件はありますか。
24. ギフティ基盤の側で、個票を見られる人を絞る（仮名ID、権限）設定はできますか。
25. 10件未満の区分を伏せた集計を、ギフティ側で作って出すことはできますか（できなければ当サービス側で加工する）。

### G. 実績の把握
26. 松本市の消防団クーポンでは「登録者のうち実際に利用したのは半数ほど」と把握されています。同じように「登録した人」「1回以上使った人」「2回以上使った人」を人単位で数えられますか。
27. 白浜町で「何度も使う人」を把握しているのは、どのデータ（会員ID・チケットID）を使っていますか。
28. 旅先納税では、寄附者の居住地（都道府県）を寄附管理システムから受け取って、利用データと紐付けられますか。

## 5. プロトタイプの画面に足せそうな指標

いまの画面（`src/components/muni/muni-dashboard.tsx` と `src/lib/metrics.ts`）は、配布・受取・利用の件数と率、月別の推移、内訳（場所・種類・事業者）、2回以上の利用、周遊、初めての利用を出している。公開情報から「e街の管理画面・データ出力で取れる見込みが高い」ものの中で、まだ出していないものを挙げる。

| おすすめ | 何を出すか | 取れる見込み | どの画面 |
| --- | --- | --- | --- |
| 1. 使われた金額 | 事業ごと・ギフトごとの決済金額の合計、1回あたりの平均金額 | 高い（売上の自動集計・精算データ）。CLAUDE.md の指標表にも「使われた金額」があるのに画面にない | ⑥自治体、⑩企業（合計だけ） |
| 2. 加盟店別の精算額 | 加盟店ごとの利用件数と金額。締日ごとの確定値 | 高い（加盟店別の精算データを締日ごとに自動生成） | ⑥自治体（企業には出さない） |
| 3. 時間帯・曜日 | 利用が多い曜日と時間帯 | 中（決済日時は画面に出ている。出力に入るかは確認 5） | ⑥自治体の内訳に1つ追加 |
| 4. 受取から初めての利用までの日数 | 受け取ってから使うまで何日かかったか（中央値） | 中（受取日時と利用日時の両方が要る。確認 5・6） | ⑥自治体 |
| 5. 未利用・期限切れ | 期限が近い未利用枚数、期限切れの枚数・金額 | 中（有効期限は券種に設定されている。失効の出力は確認 9） | ⑥自治体（リマインドの判断に使える） |
| 6. 利用者数（人単位）と1人あたり利用回数 | 「1回以上使った世帯」「2回以上使った世帯」を件数とは別に | 中（白浜町・松本市で人単位の把握の事例あり。確認 26・27） | ⑥自治体、⑩企業の「届いた世帯数」の根拠 |
| 7. 決済方式の内訳 | QR／スタンプ／紙券 | 中（確認 10） | ⑥自治体（運用の参考） |
| 8. 登録数と利用者の差 | 登録したが一度も使っていない人数 | 中（松本市の消防団クーポンで把握の事例あり） | ⑥自治体（周知の判断に使える） |

- 企業ダッシュボード（⑩）は「数字は少なく」なので、足すなら **1（使われた金額の合計）だけ**がよい。2〜8 は自治体の画面向け。
- 画面ではモックのまま「データ元：e街の利用明細（確認中）」のような注記をつけておくと、打ち合わせで取れる・取れないを確かめやすい（解釈）。

## 6. 確認できなかったこと

- **giftee for Business API 仕様書の本体**（申込みサイトのアカウント登録後にダウンロード）。参照 API のレスポンスの全項目、特に「利用済み」「利用日時」を表す項目の有無。
- **e街の API 仕様**。「API等外部連携に対応」「API発行」とはあるが、読み出し用の API（利用履歴・受取履歴を取る API）があるか、項目、認証、更新頻度は公開されていない。
- **e街の管理画面の実際の画面と出力ファイルの項目**。資料請求・問い合わせで出る資料に載っている可能性がある。
- **「受取」の定義**（シリアル入力・マイページ取得・URL を開いた、のどれか）。
- **利用後のアンケート**に対応しているか。設問を自治体が変えたときすぐ反映されるか。
- **会員登録の項目を事業ごとに自由に決められるか**。
- **加盟店マスタの属性**（市町村・業種・地区）を持てるか、出力に付けられるか。
- **寄附企業などの第三者へ集計値を出すこと**についての、ギフティ側の規約・条件。
- デジタル庁「デジタル実装の優良事例を支えるサービス／システムのカタログ」の e街プラットフォームのページ（digiden-service-catalog.digital.go.jp）は、調査時に接続できず読めなかった。
- gifteeスタンプの旧プレスリリース（giftee.co.jp/giftee_stamp/）は 404 で読めなかった。
