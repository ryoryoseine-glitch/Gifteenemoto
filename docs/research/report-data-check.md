# 報告書の数字とギフティ（e街）のデータの突き合わせ

調査日：2026-09-29
対象：`report-checklist.md` の「ギフティのデータに関わるもの」D1〜D9
土台：`giftee-api.md`（公開情報の調査結果）。今回は松本市・旅先納税の利用者向けページを追加で読んだ。
書き方：公開情報に書いてあることだけを書いた。確認できないものは「不明」とし、4章の確認事項に回した。解釈には「（解釈）」と付けた。

## 1. 要約
- **出せる見込みが高いもの**：D2（配布・受取・利用の数と利用率）、D6 の「使われた金額」、D3 のうち加盟店別の数字。e街は「管理画面からチケットの発行・受取・利用実績をリアルタイムで確認」「データのダウンロードも可能」「加盟店別や利用者属性別の分析」と公式に書いている。
- **不明なもの**：D1、D3 のうち登録項目との掛け合わせ、D4、D6 の期末の確定値、D7、D8 のうち「初めて利用した世帯」、D9 の任意の日付での締め。
- **新しく作る必要があるもの**：D5 の利用後アンケート。公開情報にあるアンケートは受け取る前に答える「取得条件」型だけ。
- **報告書のつくりに影響する事実**：
  1. 松本市は「会員登録はご家庭につき1回」だが、家族で共有するには「共有先のご家族が新規会員登録をしている必要があります」。1世帯に複数のアカウントがありうるので、アカウント数は世帯数にならない。
  2. 松本の子育て支援クーポンは令和6年度に電子化した（令和5年度までは紙）。券種名は「R6 ファミサポ 3歳未満児クーポン」のように年度つきで、有効期限は 2025-03-31。
  3. 精算データは「締日ごとに加盟店別に自動生成」。実績は管理画面にリアルタイムで反映される。締日は公開されていない。
  4. 旅先納税はメールアドレスで会員登録し、「寄附履歴」に寄附の日時・金額が残る。決済金額の誤りは「24時間以内であれば対応可能」。

## 2. D1〜D9 の突き合わせ表
凡例：確認済み＝画面・CSV で出せると公開情報で確認／可能性が高い＝同じ種類のデータは確認できたが、報告書に要る形で出るかは未確認／不明／新規＝新しく作る必要がある

| ID | 出せるか | ギフティ側のデータ | 粒度／締め | 報告書で使うときの注意 |
|---|---|---|---|---|
| D1 受益者数（重複除く）＝C5 | 不明 | 会員情報、利用実績 | 会員情報は出力できると確認済み。利用明細に会員IDが入るかは不明／締めは不明 | 重複を除くには利用明細に会員ID・チケットIDが要る。松本は家族共有で1世帯に複数アカウントがありうる。世帯でまとめるには、共有の記録か LINE 申請の単位との対応づけが要る（どちらも出力できるか不明）。券面には子どもの名前が出るので、子ども単位か世帯単位かを報告書で決めて書く。旅先納税はメール単位なので人数の近似にしかならない |
| D2 配布・受取・利用・利用率＝C5 | 件数は確認済み。「受取」の定義は不明 | 発行実績、利用実績 | 画面ではリアルタイムの集計。ダウンロードの粒度は不明 | 「受取」の時点（シリアル入力か、マイページへの取得か）を C7 に書く。回数券は「枚」と「人」で利用率が変わるので単位をそろえる。紙券と合算するかどうかを書く |
| D3 地域別・属性＝C5 | 加盟店別は確認済み。市町村・地区別は可能性が高い。登録項目別は不明 | 利用実績、加盟店別の精算データ、会員情報、周遊データ | 精算データは締日ごと | 市町村別は、加盟店マスタに市町村の項目があるかによる。登録項目との掛け合わせには「属性情報とチケットIDの紐付けが必要」。「地区」が使った場所か住んでいる所かを分けて書く。10件未満の区分を伏せる処理は当サービス側でやる |
| D4 前年同期・前年度＝C6 | 不明 | 前年度の発行実績・利用実績 | 保存期間は不明 | 松本は令和6年度が電子化の初年度なので、e街の前年比は令和7年度から。紙の年度と比べるなら、自治体が持つ紙の実績を別のデータ元として書く。年度ごとに作り直す券種（R6 → R7）を同じ事業として対応づける方法は不明 |
| D5 アンケートと利用の紐付け・n＝C6・C7 | 取得条件型は確認済み。利用後型は新規 | アンケート（取得条件）、利用実績 | 不明 | 取得条件型は使う前に答えるので、満足度や「なかったら利用したか」は聞けない。利用後アンケートと利用明細をつなぐには、e街から仮名IDを受け取れる必要がある（不明）。回答率の分母は D1 の答えに左右される |
| D6 使われた金額・期末の確定＝C2・C13 | 金額は確認済み。期末の確定値は不明 | 精算データ（加盟店別）、利用実績（決済金額） | 精算データは締日ごと、実績はリアルタイム | 締日は公開されていない。3月末で期限が切れる券種は、最後の締めで金額が決まるが、その確定日が報告に間に合うかは不明。24時間以内の訂正が、締めた後の明細にどう残るかは不明。回数券の金額が「単価×枚数」なのか、精算データに金額があるのかを確認する |
| D7 寄附企業（券種）ごと＝C2・C5 | 可能性が高い | 券種設定、発行実績、利用実績 | 不明 | 1事業に複数の券種を設定できる（松本8券種）。1券種を按分する場合は、その方法を C7 の限界に書く。寄附額による按分（C2）と券種ごとの実績は別物なので、どちらを使ったかを明記する |
| D8 KPI の実績値＝C4 | 利用世帯数は不明（D1 と同じ）。初めて利用は不明。周遊は可能性が高い | 利用実績、会員情報、周遊データ | 不明 | 「初めて利用した世帯」には、そのサービスを過去に使ったかの情報が要る。e街で分かるのは「このクーポンを初めて使った」まで。サービス自体の利用歴は自治体の台帳かアンケートで補う |
| D9 9月末・3月末で締める＝C4・C6 | 可能性が高い（e街は不明） | 発行実績、利用実績、精算データ | 任意の期間で締められるかは不明 | リアルタイムの画面は後から数字が動くので、締めた日の値を固定して保存する運用が要る。締日が月末でなければ、明細を日付で切る |

## 3. 「ギフティに確認中」と注記すべき項目
- C5：受益者数（世帯）、属性別の集計、市町村別
- C6：前年同期比
- C6・C7：アンケートの前→後、回答率
- C2・C13：期末の精算額
- C2・C5：寄附企業ごとの実績
- C4：初めて利用した世帯数、9月末・3月末で締めた値

## 4. ギフティへの確認事項（優先度順）
1. 利用明細は1回の決済ごとか。会員ID（仮名）・チケットID・券種・加盟店ID・決済日時・金額・利用枚数・取消／訂正の印は入っているか。→ C5・C6・C7・C4
2. 家族共有で分かれたアカウントを、世帯としてまとめられるか。共有の記録は出せるか。LINE で申請したときの単位と、ポータルの会員IDは対応づけられるか。→ C5
3. 券種ごとに発行・受取・利用・金額を出せるか。企業ごとに券種を1つずつ作る運用に問題はないか。→ C2・C5
4. 精算データの締日はいつか。3月末で期限が切れる券種の確定はいつか。締めた後の訂正・取消はどう反映されるか。→ C2・C13
5. 任意の日付で区切った集計を出せるか。過去の時点の値を再現できるか。→ C4・C6
6. 登録項目を事業ごとに自治体が決められるか。その項目を利用明細と会員IDで紐付けて出せるか。→ C5
7. 前年度のデータはいつまで残るか。R6 → R7 のように作り直した券種を、同じ事業として並べて出せるか。→ C6
8. 消し込みの直後に、アンケートかアンケートへのリンクを出せるか。その時に、利用明細と対応づく仮名IDを渡せるか。→ C6・C7・C8
9. 「受取」は何の時点か。受取日時は明細に残るか。→ C5・C7
10. 加盟店の登録情報に市町村・業種・地区を持てるか。「周遊データ」はどんな形で出せるか。→ C4・C5
